# Changelog

## 0.5.0 — 2026-10-22

### 新功能：超出上下文窗口的会话，先压缩再导入/导出

**问题**：一条成熟会话可能比模型能读的窗口还大。DSH 的 agent 自己会拒绝这种请求并报
`CONTEXT_WINDOW_EXCEEDED`（实测上限 1,048,576 tokens，其中 256,000 是这一轮要求的输出）。
以前插件照原样写入：会话能出现在侧边栏，但**第一句话就失败**——用户拿到的是一个打不开的会话。

现在导入和导出都先过 `lib/host/compress.js`，四阶段阶梯、全本地、**不调用模型**。
排序原则是**续聊最需要什么就最后动什么**——跑偏通常不是因为少了几行日志，而是因为不知道前面做过什么、
结论是什么：

1. **截断单条**：单条工具输出 → 约 4000 字符（头 70% + 尾 30%，中间标注省略字符数）、超长正文 → 约 8000、
   工具参数 → 约 2000；**思考块整段丢弃**（续聊用不到，往往又是最大的一块）。回合与结论一个不少。
2. **精简中间**：只动较早的中间回合——工具输出收成 400 字符存根（还看得出是什么命令、结果多大），
   长正文收到一段；**每一轮的提问和结论都保留**。这一步之后，整段对话仍然读得懂、接得上。
3. **省略中段**：还是超才丢整段，并换成**一条逐轮摘要**：`- 第 k 轮 · 用户：诉求 · 结论：回答`
   （140/170 字截断）+ 期间用到的工具 + "需要细节请让用户提供，不要凭空推断"。这是防跑偏的关键：
   早期版本只写"省略了第几到第几轮 + 主题列表"，模型知道缺东西却不知道缺什么，容易自己编。
4. **兜底**：只剩一两个巨型回合时按比例压缩正文。

阈值：`预算 = 上限 − 预留输出`，再乘 0.85（估算器按"中日韩字符 1 token / 英文 3.6 字符"折算，不是真
tokenizer，要留余量）；默认约 67 万 tokens 以下不动，可用 `contextLimit` / `completionReserve`
或 `DSH_SESSION_CONTEXT_LIMIT` / `DSH_SESSION_COMPLETION_RESERVE` 覆盖。

**接进来的位置**：

- `reimport.js` 的**整份写入**分支（首次导入、打开时另建、`merge:false` 覆盖、busy/conflict 兜底、
  最后的重写）先压缩，`merge` 分支**不压缩**（追加改不了已存历史），超上限时只在结果行提示；
- `export-service.js` 在交给 sink 之前压缩，**dry-run 计划也基于压缩后的会话**，所以计划卡片上
  看到的就是真正会落盘的内容；
- 结果行/计划卡片显示：`历史约 1.03M tokens，超出上下文上限（上限 1.05M，预留输出 256k），
  已压缩到约 619k tokens：截断 92 条工具输出、去掉 687 段思考过程`；走到阶段 ② 会多一句
  「精简中间 N 轮的工具细节（保留每轮诉求与结论）」。

**顺带堵住一个坑**：压缩过的会话，存下来的是**改写版**，逐回合比对必然错位，再次导入时若走增量合并
会把整段历史复制第二遍。现在状态里记 `compression`，这类会话再导入直接**整份重写为最新压缩版**，
并在结果行写明“如果你在 DSH 里续聊过，那些回合会丢失”。

**面板**：导入页脚与导出选项各加一个「超长自动压缩」勾选框（默认开、localStorage 记住），
关掉就按原样写入；`options.compress: 'off'` 等价。

**实测**：本机最大的一条 DSH 会话（1.3 MB / 61 回合）估算 1,032,193 tokens ——正是之前导出/导入时
报上下文超限的那条。默认阈值下压到 **619,189**，只用到阶段 ①②（92 条工具输出截断、687 段思考丢弃），
**61 个回合一个没少**；人为把窗口压到 6 万时才走到阶段 ③，摘要里仍逐轮保留 56 轮的诉求与结论。

- 测试 106 → 120（`test/compress.test.mjs` 10 条 + reimport 2 条 + export 2 条），其中一条专门断言
  阶段 ②「每一轮的提问和结论都必须保留，只准收窄工具噪音」。
- 文档：`docs/usage.md` 新增 1.4「超长历史先压缩再写入」（后续小节顺延为 1.5/1.6/1.7）、
  FAQ 两条、README 功能段落。

## 0.4.5 — 2026-10-22

### 恢复：原会话打开时仍然「导出一条新会话」，但把原因写清楚

0.4.4 曾改成「跳过、什么都不写」，会丢掉来源新增的回合。现恢复为**在旁边导入成一条新会话**（原会话不动、内容不丢），
并在结果行明确写出两点，避免用户以为是 bug：

这就是「二次导入后多一条、还落在未分类」的完整解释：**合并做不了 → 新建一条 → 来源没有项目目录 → 只能未分类**。
文档同步：`docs/usage.md` 1.5 表格、FAQ「为什么在未分类里」、`README.md` 功能说明。

- 测试仍为 106（把 0.4.4 的「零写入」用例改回「新会话 + 两条说明」）。

## 0.4.4 — 2026-10-22

### 改动：原会话正在打开时不再新建副本，改为「跳过 + 说明」

以前二次导入一个**正在 DSH 里打开**的会话时，合并做不了，就退化成「导入为新会话」——于是一次导入多出一条，
来源没有项目目录时这条新会话还会落在「未分类」，看起来像「二次导入跑到未分类」。

现在这一支**什么都不写**：不写原会话（运行中的会话会把内存副本刷回磁盘，写了也会被覆盖），也不新建副本。
结果行标为「跳过」并写明：`原会话正在 DSH 里打开：本次没有写入，也没有新建副本。关掉那条会话后再导入一次，
就会增量合并到它里面。` 来源内容不会丢，关掉标签页后再点一次导入即可合入。

**为什么不做「自动关闭再覆盖」**：查过宿主实现（`app.asar`）——`SessionStore` / `AgentFactory` 都没有对外的
`close(id)`，会话只在自己所属 fiber 卸载时销毁；`session/close` 是 ACP 层给**客户端 UI** 用的请求，
宿主插件拿不到那条连接。所以插件无法替用户关闭会话，只能等它真的关掉。

- 测试 105 → 106（新增「打开时再次导入零写入」，并把原「导入为新会话」用例改为断言跳过）。

## 0.4.3 — 2026-10-22

### 加固：导入后的工作区归属会被验证并修复

排查「导入到 DSH 不认工作区 / 落在未分类」时，把 DSH 自己的分组实现读了一遍（`WorkspaceRegistry` +
`Workspace.attachSession` + 侧边栏的 `owningGroupKey`）。结论：侧边栏分组**只看工作区成员表**，而成员表会被
DSH 的 cwd 索引过滤，且 `attachSession` 对「已经是成员」的会话**直接返回、不再校验**。于是有三种情况会让
会话停在「未分类」，插件以前无法发现也无法纠正：

- 会话是成员，但它的 cwd 变了（重导入整份重写、项目被移动/改名），DSH 的索引还是旧的 → 成员被过滤掉；
- 会话同时挂在多个工作区（历史遗留）→ 侧边栏显示重复/错位；
- `attachSession` 抛错时只有一条 warning，用户不一定看得到。

现在的做法（`service.js`）：

- 附加后**回读成员表验证**是否真的生效；没生效就 `detachSession` → `attachSession` 重跑一次校验，
  把 DSH 的 cwd 索引刷新（这是唯一能修好「成员但被过滤」的路径）；
- 会话只应属于「路径等于它 cwd」的那一个工作区，其他工作区上的同名成员一律 `detachSession` 掉；
- 仍然失败的，返回明确原因（「工作区认为这条会话的目录不匹配…侧边栏可能仍把它放在未分类」），不再静默。
- 测试 102 → 105。

### 核实：导入方向没有「导出多一条」那种 id 问题

- 导入的是 *合并* 到 `imported.json` 记录的那条 DSH 会话（不是按来源 id 造新 id），所以重复导入不会多出会话；
- 本机 3 条有内容的导入会话全部归组正确（`2026-10-22-08-48-48`、`AI工作台`、`DeepHarness`）；
- 落在「未分类」的两种情况是设计如此：来源会话的 cwd 是**用户主目录**（DSH 拒绝把 cwd≠工作区路径的会话挂进去），
  或者来源项目目录**已不存在**。面板行尾会写明 `· 未分组（来源会话没有指定工作区）`。

## 0.4.2 — 2026-10-22

### 修复：会话来回导一次，WorkBuddy 里就多出一条同名会话

- 导出时目标 id 是从 **DSH 会话 id** 推出来的（`session-fe2b7f0b…` → `fe2b7f0b…`）。但导入方向
  给会话分配的是一个新的随机 uuid，所以「WorkBuddy `584b5e3f` → DSH `session-fe2b7f0b` → 再导出」
  会写出 `fe2b7f0b.jsonl`，原会话 `584b5e3f.jsonl` 一动不动 —— 侧边栏于是出现两条同名、同项目的会话，
  用户往往要手动删掉那条副本。
- 现在导出会先查导入映射（`$DSH_HOME/session-import/imported.json`），把会话**写回它原来的那条会话**：
  计划里会说明「本次写回原会话 …（不新建副本）」，覆盖前照旧自动备份。原生 DSH 会话（没有来源记录）
  行为不变，仍然按 DSH id 推导，重复导出天然幂等。
- 回写时优先落在**原本就存着该 id 的项目目录**里：如果导入后 DSH 会话的 cwd 变了，仍然写回原目录，
  避免同一个 id 出现在两个项目文件夹下又被算成两条会话。
- `originId` 只是建议值：形状不合法（不是 UUID）就退回旧逻辑，不会因为映射表脏了而让原本能用的导出失败；
  显式传入的 `sessionId` 优先级仍然最高。
- 已知限制：0.4.1 及更早版本导出的副本不会被自动合并，仍然需要手动删一次（删掉的那条不影响原会话）。

## 0.4.1 — 2026-10-22

### 修复：二次导出报「EPERM: operation not permitted, rename」

- Windows 上覆盖已存在的会话文件时，`rename` 可能被 `EPERM` 拒绝 —— 目标应用正在运行时它的
  文件监视器、杀毒软件或搜索索引器会短暂持有旧文件句柄，第一次导出（目标不存在）不受影响，
  第二次更新就会失败。
- `atomicWrite` 现在分三级恢复：① 重试改名（最多 5 次，退避递增）；② 删除目标后再改名；
  ③ 降级为复制（临时文件已 fsync、原文件已有备份，内容不会丢失）。降级发生时计划/结果里会提示
  「目标文件被其它程序短暂占用…内容不受影响」。
- 非 EPERM/EACCES 的错误仍然立即抛出，不掩盖真实问题。

## 0.4.0 — 2026-10-22

### 改进：导出的会话默认「完全权限」

- 写进 WorkBuddy 的会话索引现在把 `permission_mode` 设为 **`fullAccess`**。之前写的是 `default`，
  而 WorkBuddy 按这一列决定会话的权限级别：`default` 下每个工具调用都在等一次批准，导入的会话
  历史里没有这条批准记录 —— 于是表现为「导入导出之后 agent 命令执行不了」。
- 重复导出时**保留用户在 WorkBuddy 里手动改过的权限**（读旧行再写回）；只有新建或从没有权限值的
  会话才落到 `fullAccess`，不会把用户的选择每次覆盖掉。
- 已把本机两条历史导入会话就地更新为 `fullAccess`（改库前自动备份 `workbuddy.db.bak-plugin-*`）。
- 说明：DSH 会话头本身不存权限级别（只有 cwd / origin / agentPreset），所以导入方向（WorkBuddy → DSH）
  没有对应字段要写，问题只出在导出方向。

## 0.3.3 — 2026-10-22

### 修复：重复导入同一个会话改为「合并」，不再整份覆盖

- 以前重复导入是「删掉旧会话 + 按来源重写一遍」。只要你在 DSH 里接着聊过，那几轮本地
  对话就会随旧会话一起被删掉——这正是用户反馈的问题。
- 现在重复导入是**追加式合并**：读回原会话的日志，与来源对话逐回合比对，找出两边的共同
  前缀（也就是上次导入已经写过的部分），只把来源**新增**的回合追加到原会话末尾。全程不
  删除任何东西，所以：
  - 你在 DSH 里的本地追问、压缩摘要都保留；
  - 来源没有新内容时**一个字都不写**，结果行显示「已是最新，原会话没有变化」；
  - 合并失败时原会话保持原样，不会留下半截日志。
- 追加的事件序号接着原日志往下排（`assertContiguous` 要求从 0 连续），回合号同样接续，
  时间戳不早于原日志的最后一条——日志结构仍然完全合法，能正常打开、续聊、导出。
- 新增 `【导入说明】` 的剥离：比对前先把首次导入写入的说明去掉，否则第 1 个回合永远对不
  上，任何重复导入都无法识别重叠部分。旧版本写入的、措辞已变化的说明也能被「来源是原
  文本后缀」这一条兜住。
- 原会话正在 DSH 里打开时**绝不写入**（它内存里有一份，落盘会把写入覆盖掉）：改为导入成
  新会话，并提示把旧的手动删掉。合并时被别的持有者抢走写锁（`busy`）同样按这条处理。
- 读取到写入之间原日志被改动（序号校验失败）时报 `conflict`，同样退到新建会话——绝不在
  别人正在写入的会话上做整份重写。
- 只有在必须兜底时才整份重写，且结果会如实说明是哪一种：`已整份重写该会话`，或
  `也无法覆盖原会话，已导入为新会话`。
- 导入结果行新增 `merged` / `addedTurns`，文案为「已合并到原会话，续接 N 个回合」。
- `options.merge: false` 可退回旧的覆盖行为。
- 新增 `lib/host/merge.js`（比对 + 追加）与 `lib/host/reimport.js`（重导入策略：合并 →
  打开中 → 抢锁 → 整份重写），`runJob` 里的分支判断收敛成一个 `persistConversation`。
- 新增 `test/merge.test.mjs`（21 项）。测试总数 71 → 92。

## 0.3.2 — 2026-10-22

### 新增：导入到 DSH 后自动归入对应工作区

- DSH 的侧边栏按**登记的工作区**（`$DSH_HOME/storages/workspace.json`）分组，不是按会话
  自己的 `cwd` 分组；导入走的是会话持久化接口，绕过了工作区登记，所以以前所有导入的会话
  都堆在「未分组」。
- 现在导入一条会话后会：按来源的项目目录找到已有工作区，没有就新建一个（标题取目录名，
  例如 `DeepHarness`），再把会话 `attachSession` 进去。同一目录反复导入只会复用一个工作区。
- 原对话没有项目目录（无 cwd、目录已不存在、或就是用户主目录）时不建工作区，仍落在
  「未分组」——「纯会话」不该被塞进一个虚构的工作区。
- 工作区服务不可用或 attach 被拒时只记一条警告，**不影响会话导入本身**。
- 导入结果行新增去向说明：`· 已归入工作区「X」` / `· 已新建工作区「X」` /
  `· 未分组（原对话没有工作区信息）`；完成提示同步改写。
- 接口新增 `options.groupByWorkspace`（默认 `true`），需要保持旧行为时可传 `false`。
- 新增 `test/workspace.test.mjs`（7 项）。测试总数 64 → 71。

## 0.3.1 — 2026-10-22

### 改进：「导入到其他 agent」只列页面上看得见的会话

- 左栏来源改成 DSH 页面自己的会话列表（浏览器侧 `ctx.sessions.list`），不再扫
  `~/.dsh/sessions/**` 后全量列出。效果：
  - 别的 workspace 里没出现在页面的会话、被页面隐藏的会话不再混进列表；
  - 子 agent 会话（`[dsh-*:delegated]` 这类，页面上只能从父会话进入）不再单列；
  - 空白会话（还没发过消息）不再出现——它们以前能被选中、点「开始导入」才报
    「没有可导出的内容」。
- 面板打开期间会跟随会话列表变化：新建会话自动出现，删掉的自动消失。
- 左栏标题下增加一行说明 `只列出页面上的 N 个会话（本机共 M 个）`，避免看起来像丢条目。
- 这个 DSH 版本没有会话列表服务时，退回列出本机全部会话并提示原因。
- Host 端点 `POST /session-export/sources` 新增可选 `ids`，返回
  `{ conversations, pageOnly, total, hidden }`；不传 `ids` 行为与以前一致。
- 新增 `test/client-scope.test.mjs`（3 项，直接加载构建产物验证范围），
  `test/export.test.mjs` 增 3 项。测试总数 57 → 63。

## 0.3.0 — 2026-10-22

### 新增：把 DSH 会话导入到其他 agent（双向互导的另一半）

- 面板增加「导入到其他 agent」标签页，把本机 DSH 会话写进本机第三方 agent。当前支持 **WorkBuddy**
  （写入 transcript + 注册 `workbuddy.db` 的 `sessions` 表，侧边栏可见）。
- 两段式写入：不传 `confirm` 只返回计划（目标文件、行数、是否覆盖、备份路径），
  看过计划再确认才落盘；覆盖前自动备份 transcript 与数据库；目标应用运行中拒绝写入。
- sink 架构与 provider 对称（`lib/host/sinks/`），新增目标见
  [docs/adding-sink.md](docs/adding-sink.md)。未实现的目标缺少 `write` 会被安全跳过。
- 目标没有会话索引时不再拒绝，改为首次导入创建最小表结构（列从写入行派生，
  避免 `no such column`）；`workbuddyHome()` 修正覆盖路径解析，索引不再落到上一级目录。
- 该方向端点同时接受 `{ id, target, options }` 与扁平 `{ sourceId, targetId, … }` 两种载荷。

### 新增：同一会话再次导入时覆盖

- 导入记录里已有 `sessionId` 时，再次导入同一个远程会话会**复用该 id 重写**原 DSH 会话，
  不再留下重复副本。后端提供删除入口时先删除再写入（`replaced: true`）；不提供时降级为
  新建，并在导入结果里明确提示「原会话仍保留，可手动删除」。
- 面板的导入结果显示「已覆盖原会话」，与首次导入区分开。
- 新增 5 项测试（`test/reimport.test.mjs`）覆盖首次导入、覆盖、无删除能力降级、默认不删、
  非法 id 归一化。

### 修复（导入到其他 agent 方向）

- 读取 DSH 会话时工具调用重复计数：`tool/result` 在更晚的 run 才到达（并行调用、子代理续跑）
  时结果被挂到错误的 run 上，「补齐配对」又合成第二个工具调用块。实测 191 次调用的会话被
  读成 195 个块。改为按调用 id 全局定位归属 run，配对修复也用全局键，21 个真实会话精确对齐。
- 写入时思考内容被并进正文（`【思考】` 前缀），导回后思考变成普通正文、思考计数归零。
  改为按真实 WorkBuddy 格式写成独立的 `reasoning` 事件。
- 截断标记每次往返叠加：该方向的 `clampText` 改为幂等（导入到 DSH 侧的 `clamp` 未改动）。
- WorkBuddy 导入的用户提示提取改为注入标签白名单（`system-reminder`、`current_time`、
  `previous_*` 等 19 个）。原通用规则 `/<[a-z_][^>]*>/g` 会删掉用户正在讨论的
  `<view>`/`<text>`/`<div>` 以及 `` `<id>.json` `` 这类文本。该改动只影响 workbuddy 来源，
  其他 provider 与导入流程结构均未变动。
